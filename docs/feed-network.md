# 피드 네트워크 수신과 진단

GeekNews 목록은 공식 Atom 피드, Hacker News 목록은 Algolia API를 사용한다.
기사 본문은 두 소스 모두 Jina Reader에서 Markdown으로 변환한다. 따라서 목록이 열려도
본문 변환 서버와의 연결이나 원본 사이트의 접근 제한 때문에 기사 열기가 실패할 수 있다.

## 분할 수신 보완

설치된 Arduino 프레임워크의 `NetworkClient::readBytes()`는 `read()`가 음수이면 즉시 반환한다.
그러나 `NetworkClientSecure::read()`는 연결이 살아 있어도 현재 읽을 데이터가 없으면 `-1`을 반환한다.
HTTP 청크 뒤의 `\r\n`이 따로 도착하면 두 바이트를 모두 기다리지 않고 짧은 읽기로 실패할 수 있다.

피드 전용 `FeedSecureClient`는 이 경우 마지막 수신 이후 제한 시간까지 기다린다.
연결이 종료되면 짧은 읽기를 반환하고, 제한 시간을 초과하면 연결을 종료한다.
HTTP 헤더·청크 해석은 계속 Arduino `HTTPClient`가 담당한다. 다른 네트워크 기능의 클라이언트는 바꾸지 않는다.

기사 본문은 SD 임시 파일로 스트리밍하며, 완전 수신과 저장 성공을 확인한 뒤에만 표시한다.
GeekNews의 줄 길이 제한은 HTTP 수신 블록 크기가 아니라 실제 줄에 적용한다.
본문 48 KiB, 한 줄 4 KiB 제한은 유지한다. 잘린 응답을 정상 기사로 취급하지 않는다.

새 목록이나 기사를 불러오기 전에는 이전 기사 레이아웃의 용량까지 반환한다.
이 해제는 로딩 화면의 렌더링 완료를 기다린 후 수행한다. 기사 완전 수신과 SD 파일 닫기가
확인되면 본문 문자열 할당 전에 Wi-Fi를 끈다. 자동 재접속할 수 있는 저장된 접속 정보가
없으면 연결을 유지한다. 다음 네트워크 요청은 기존 저장 Wi-Fi 재연결 경로를 사용한다.

현재 공개 읽기 요청의 TLS 인증서 검증 생략 설정은 기존대로 유지되어 있다.
암호화는 사용하지만 서버 신원을 검증하지 않으므로, 인증된 연결과 동일한 보안을 제공하지 않는다.

## 긴 기사의 RAM 저장 공간 확장

기사 전체 512줄에서 고정적으로 중단하던 제한을 제거했다. 화면 배치 데이터는 계속 RAM에 두고,
필요한 시점에 줄 128개·스타일 구간 256개·텍스트 4 KiB·페이지 위치 32개 단위로 확장한다.
전체 상한만큼 미리 할당하지 않는다. 텍스트는 문자열의 내부 용량 증가 정책을 피하기 위해
연속 문자 벡터에 저장하며, 각 스타일 구간의 끝에는 기존처럼 널 문자를 넣는다.

확장 전에는 새 버퍼 전체를 할당할 여유 메모리와 연속 빈 공간을 검사한다. 재할당 중에는
기존 버퍼도 살아 있으므로 증가분만 검사해서는 안 된다. 안전 여유 8 KiB를 유지할 수 없으면
확장을 중단하고 메모리 부족 진단을 표시한다. 기존 공간에 들어가는 데이터에는 재할당하지 않는다.

무제한 확장이 아닌 안전 상한은 8,192줄·8,192개 스타일 구간이다. 텍스트는 16비트 오프셋과
호환되도록 구간 끝의 널 문자를 포함해 65,535바이트로 제한한다. 상한 초과는 실제 메모리 부족과
구분하여 기사 화면 데이터 한도 초과로 표시한다. 가용 RAM이 부족하면 상한 전에 중단할 수 있다.

앞뒤 페이지 이동은 RAM의 줄 위치 목록을 사용하며 Wi-Fi나 SD 읽기를 하지 않는다.
실험적으로 추가했던 SD 화면 저장 코드와 테스트는 제거했다. 기존 다운로드용 SD 임시 파일,
48 KiB 본문 제한, GeekNews 원문 한 줄 4 KiB 제한, 스크랩·QR·전면/측면 페이지 버튼은 유지한다.
실험 빌드가 SD에 남긴 `/.crosspoint/feed_layout.tmp`가 있다면 더 이상 사용되지 않으며 수동 삭제해도 된다.

## 실패 화면의 진단 값

오류 설명 아래에 마지막 요청의 진단 값이 표시된다. 예를 들어 `B -11 | 2048/-1 B | 60s T`는
본문 단계에서 2,048바이트를 받은 후 시간 초과한 경우를 뜻한다.

- `H`: 연결·요청·응답 헤더 단계, `B`: 응답 본문 단계
- 다음 숫자: HTTP 상태 코드 또는 Arduino HTTPClient의 음수 오류 코드
- `수신량/예상량 B`: 저장 처리기에 전달한 바이트 수와 Content-Length. `-1`은 서버가 길이를 알리지 않은 경우
- `s`: 해당 요청의 경과 시간. 자동 재시도 전체 시간이 아니다.
- `S`: 본문 처리기 또는 저장 실패, `T`: 보완된 본문 읽기의 시간 초과

기사 전체의 실패 여부는 위쪽 오류 설명을 기준으로 한다. 예를 들어 수신은 성공했어도 이후
Markdown 처리나 SD 파일 읽기가 실패하면 진단 값은 HTTP 200을 표시할 수 있다.
SSID, 암호, 기사 URL과 본문은 진단 값에 포함하지 않는다.

메모리 관련 실패에는 `M`으로 시작하는 추가 진단이 표시된다.
`READ`는 SD 본문 버퍼, `LINES`·`SPANS`·`TEXT`·`PAGES`는 화면 데이터 할당 실패다.
`need`는 요청한 바이트 수이며 `heap`은 여유 메모리, `max`는 가장 큰 연속 빈 공간이다.
안전 여유분을 남겨야 하므로 요청량보다 큰 빈 공간이 있어도 할당을 중단할 수 있다.
`LINE-LIMIT`·`SPAN-LIMIT`·`TEXT-LIMIT`는 실제 RAM 부족이 아니라 화면 데이터의 상한 초과다.
이제 이 제한은 RAM 레이아웃의 안전 상한에 적용되며, 기사 전체 512줄 제한은 아니다.
상한 초과 시 `need=0`은 추가 할당을 시도하지 않았다는 의미다.

## 검증

```powershell
python test/network/verify_feed_transport.py
python test/config/verify_geeknews_feature.py
python test/config/verify_feed_memory_lifecycle.py
python -m platformio run -e default
```

첫 테스트는 C++20 컴파일러의 `static_assert`로 실제 수신 및 용량 확장 함수를 평가한다.
분할된 구분자, 수정 전 조기 반환 재현, 수신 진행에 따른 대기 시간 갱신, 연결 종료,
무응답 제한 시간, 빈 읽기, 32비트 시계 순환을 확인한다. 호스트 컴파일러가 없으면 설치된
PlatformIO RISC-V 컴파일러를 사용하며 테스트용 바이너리를 기기에서 실행할 필요는 없다.
합성 데이터 1,300줄·2,600개 구간의 단계적 확장, 기존 데이터 보존, 새 버퍼 전체 할당량 검사,
부족한 메모리에서 확장 거부, 재할당 없는 기존 용량 재사용, 상한 및 정수 넘침도 검사한다.
실제 기사의 줄바꿈·페이지 출력과 기기 메모리 상태는 플래시 후 확인해야 한다.

이 테스트와 빌드만으로 실제 Wi-Fi/TLS 연결의 안정성을 보장하지는 않는다.
전체 플래시 후 두 소스의 여러 기사와 재시도를 확인하고, 실패하면 진단 줄까지 포함한 화면을 확인한다.
